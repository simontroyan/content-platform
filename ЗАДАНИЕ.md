# День 1. Подготовить среду и выпустить сервис

## Ситуация

Разработчик передал исходный код первого API контент-платформы. Команде нужно отдельное локальное Kubernetes-окружение, в котором можно запускать и обновлять сервис. Приложение ещё не упаковано и инфраструктурные файлы не написаны. Ты отвечаешь за их создание и проверку.

Время: до 5 часов. Решай самостоятельно. Условие и ограничения намеренно не содержат готовых команд, манифестов и указания причин. Если застрянешь, попроси подсказку; можно пользоваться документацией. Записывай время и использованную помощь.

## Исходные данные

- `app/server.py` — сервис на стандартной библиотеке Python 3.12+. Для запуска ему не нужны внешние Python-пакеты.
- `GET /healthz` возвращает HTTP 200 и JSON со статусом.
- `GET /api/info` возвращает JSON с именем сервиса, значением `APP_ENV` и именем экземпляра.
- `PORT` задаёт порт приложения, по умолчанию 8080. Сервер слушает все интерфейсы контейнера.
- На этом Mac доступна команда Multipass; работоспособность службы и доступные ресурсы ещё нужно проверить. Docker Desktop можно использовать для сборки образа. В `trainer/.local/bin` есть отдельный `kubectl` v1.35 — проверь его совместимость с выбранной версией кластера. Существующие окружения, в том числе `shift-cka`, не изменяй.

## Твоя работа

Выполняй этапы по порядку. В каждом этапе сначала сделай действия, затем проверь результат и сохрани доказательства. Не переходи к приложению, пока кластер не проверен.

### Этап 1. Подготовь и проверь кластер

1. Проверь свободную память Mac и список уже работающих Multipass VM. Не останавливай и не меняй чужие стенды, включая `shift-cka`.
2. Выбери совместимые версии Ubuntu, Kubernetes, containerd и CNI. Запиши выбранные версии и доступные VM ресурсы.
3. Создай отдельные VM Multipass для одного control plane и одного worker. Задай им CPU и память с учётом доступных ресурсов.
4. На обеих VM проверь Linux, архитектуру и IP-адреса; убедись, что узлы могут обмениваться трафиком.
5. На обеих VM подготовь Linux для kubeadm: проверь swap и необходимые сетевые настройки ядра.
6. Установи и настрой containerd на обеих VM. Для systemd cgroup driver проверь, что в конфигурации containerd включён `SystemdCgroup = true`; затем перезапусти runtime и проверь, что он запущен.
7. Установи совместимые `kubelet` и `kubeadm` на обе VM. Установи `kubectl` в месте, откуда будешь администрировать кластер.
8. Только на control plane выполни инициализацию `kubeadm`, указав доступный worker адрес control plane и Pod CIDR, подходящий выбранному CNI и не пересекающийся с сетью VM. Сохрани выданную команду присоединения worker; не добавляй токен в Git.
9. Настрой отдельный kubeconfig в `content-platform/.work/kubeconfig.yaml`. Используй его и его контекст явно, не меняя пользовательский kubeconfig.
10. Установи выбранный CNI по его официальной инструкции. Манифест применяй к кластеру один раз: сетевые Pod CNI должны запуститься на каждой ноде.
11. На worker выполни сохранённую команду присоединения к кластеру.
12. Проверь обе ноды и системные Pod. Если что-то не готово, изучи описание Pod, события и логи, устрани причину и повтори проверку.

**Проверь и сохрани:** настройки и состояние обеих VM; версии Linux, runtime и Kubernetes; вывод `kubectl get nodes -o wide` с двумя `Ready` нодами; вывод `kubectl get pods -A -o wide` с готовыми CNI, CoreDNS и control plane компонентами; имя и контекст отдельного kubeconfig. Второй worker необязателен.

### Этап 2. Разберись в устройстве кластера

1. Получи список системных Pod всех namespace с указанием ноды, на которой каждый запущен.
2. Найди `kube-apiserver`, `kube-scheduler`, `kube-controller-manager`, `etcd`, `kube-proxy`, CoreDNS и Pod выбранного CNI.
3. Для каждого компонента запиши его ноду и роль. Отметь, какие компоненты относятся к control plane, а какие запускаются на каждой ноде или как сетевые Pod.
4. Отдельно объясни, чем работающий процесс/Pod Kubernetes отличается от объекта API, например Deployment, ReplicaSet или Service.
5. Нарисуй схему или составь таблицу размещения компонентов и проговори её своими словами.

**Этап завершён, когда** схема или таблица соответствует фактическому выводу кластера, а различие между компонентами и объектами API объяснено.

### Этап 3. Собери образ приложения и опубликуй его в Docker Hub

Работай из корня `content-platform`: именно эта папка будет контекстом сборки.

1. Создай `.dockerignore`. Исключи кэши, Git-метаданные и локальные секреты. Не исключай `app/` и `app/server.py`.
2. Создай `Dockerfile`: выбери базовый Python-образ, задай рабочую папку, скопируй проект и укажи запуск `app/server.py`.
3. В Docker Hub создай публичный репозиторий `content-api`. Для этого учебного задания публичный образ позволит нодам скачать его без отдельной настройки учётных данных Kubernetes.
4. Назначь образу тег в формате `ЛОГИН_DOCKER_HUB/content-api:v1`. Один и тот же полный тег используй при сборке и публикации.
5. Авторизуй Docker CLI в Docker Hub командой `docker login`, затем собери образ для архитектуры нод `linux/arm64` и отправь его в Docker Hub. Запускай сборку из корня проекта. Замени `ЛОГИН_DOCKER_HUB` своим логином и используй тот же тег в обеих командах:

   ```sh
   docker login
   docker build --platform linux/arm64 -t ЛОГИН_DOCKER_HUB/content-api:v1 .
   docker push ЛОГИН_DOCKER_HUB/content-api:v1
   ```

   Не помещай пароль или access token в Dockerfile, манифесты или файлы проекта.
6. Проверь в Docker Hub, что репозиторий содержит образ с нужным тегом. Запиши полное имя образа: оно понадобится в Deployment.

Документация: [Dockerfile](https://docs.docker.com/build/concepts/dockerfile/), [контекст сборки и `.dockerignore`](https://docs.docker.com/build/concepts/context/), [публикация образа](https://docs.docker.com/build/pushing/).

**Этап завершён, когда** Dockerfile и `.dockerignore` сохранены в проекте, а образ с тегом и архитектурой `linux/arm64` опубликован и виден в Docker Hub. В Kubernetes отправляется имя готового образа, не Dockerfile.

### Этап 4. Разверни приложение

1. В проекте создай папку для Kubernetes-манифестов и файл приложения, например `k8s/app.yaml`.
2. Опиши namespace `content-lab`.
3. Опиши ConfigMap со значением `APP_ENV=lab`.
4. Опиши Deployment на две реплики. Укажи опубликованный на этапе 3 образ, порт приложения `8080` и передачу `APP_ENV` из ConfigMap.
5. Добавь readiness- и liveness-пробы на маршрут `/healthz`.
6. Задай requests и limits CPU и памяти. Кратко объясни, почему выбрал эти значения.
7. Опиши Service, который выбирает Pod Deployment по меткам и направляет трафик на порт приложения.
8. Примени манифест через отдельный kubeconfig и проверь, что Deployment создал две готовые реплики, а Service получил endpoints этих Pod.

**Этап завершён, когда** манифест сохранён в проекте, у Deployment две готовые реплики, и endpoints Service указывают на эти Pod.

### Этап 5. Проверь доступность сервиса

1. Проверь, что обе реплики готовы и у Service есть endpoints.
2. Запусти временный Pod с HTTP-клиентом внутри кластера.
3. Через DNS-имя Service запроси `/healthz` и `/api/info`.
4. Проверь HTTP-ответы. В ответе `/api/info` проверь значение `APP_ENV` и имя экземпляра.
5. Проверь доступ к API с Mac, например через временный `kubectl port-forward`, и запиши выбранный способ.
6. Удали временный Pod после проверки, если он больше не нужен.

**Этап завершён, когда** сохранены успешные ответы обоих маршрутов из кластера и с Mac, а endpoints Service сопоставлены с готовыми Pod.

### Этап 6. Проверь восстановление Pod

1. До удаления запиши число готовых реплик, имена Pod и endpoints Service.
2. Удали один Pod приложения в `content-lab`.
3. Дождись, пока Deployment снова покажет две готовые реплики.
4. Проверь, что новый Pod появился в endpoints Service и HTTP-запрос к приложению снова проходит.
5. Объясни, какой контроллер создал замену и почему приложение не хранит данные между экземплярами.

**Этап завершён, когда** сохранены результаты до и после удаления: число и имена Pod, endpoints и успешная HTTP-проверка.

### Этап 7. Подведи итоги

1. Собери результаты и доказательства этапов 1–6 в краткий отчёт `ИТОГИ.md`.
2. Укажи архитектуру и версии, схему кластера, имя опубликованного образа, манифесты и способы проверки.
3. Запиши найденные проблемы, их причины и решения, затраченное время и использованную помощь.
4. Опиши ограничения учебного стенда и назови, что изменил бы для production и почему.
5. Перед сдачей проверь, что в отчёт и Git не попали kubeconfig, Docker Hub access token, пароли и другие секреты.

**Итог сдачи:** исходники и Dockerfile; настройки VM и безопасно сохранённый отдельный kubeconfig; манифесты; опубликованный образ; результаты проверок компонентов, сервиса и восстановления Pod; отчёт `ИТОГИ.md`. Автоматического проверяющего для этого дня нет: наличие файла само по себе не доказывает работающий результат.

## Ограничения

- Работай только в новом учебном кластере и его namespace. Всюду указывай свой kubeconfig и контекст явно; не трогай чужие контексты, существующий `shift-cka`, рабочие облачные ресурсы или пользовательские данные.
- Не требуется создавать облачные ресурсы, добавлять реальные секреты, PostgreSQL или систему мониторинга в первый день.
- Проверка не должна опираться только на то, что Pod имеет статус Running. Для доступности важны readiness, endpoints и реальный HTTP-запрос.
- Не удаляй кластер или результаты до разбора. Пользователь решает, когда они больше не нужны.
