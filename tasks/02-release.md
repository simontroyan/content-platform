# День 2. Pull request, CI и выпуск приложения

## Рабочая ситуация

Разработчик подготовил изменение API в отдельной ветке и открыл pull request. В нём меняется обычный файл приложения `app/server.py`, а не создаётся отдельная папка с новой копией. Ваша команда перед выпуском должна проверять изменения и собирать контейнер. Сейчас в репозитории нет готового CI: тебе нужно спроектировать и реализовать его самому.

Продолжай работать на своём кластере первого дня в Multipass. Ориентир — 5 часов, из них около 3–3,5 часов на Kubernetes и диагностику; если не хватит, фиксируем результат и продолжаем. Подсказки доступны по запросу, готовый pipeline не предоставляется.

## Задача 1. Прими изменение как инженер

1. Изучи pull request и перечисли файлы и части приложения, которые изменились.
2. Определи, что изменилось в API: маршруты, форматы запросов и ответов.
3. Оцени совместимость новой версии со старой и обоснуй вывод.
4. Определи, какими проверками можно подтвердить работоспособность изменений.
5. Зафиксируй исходное состояние кластера и явно укажи используемый контекст.
6. Запиши состояние Deployment, включая число реплик и используемый образ.
7. Запиши состояние Service и EndpointSlice.
8. Проверь и зафиксируй ответы текущего API.
9. Определи способ восстановления исходной версии до любых изменений кластера.

## Задача 2. Построй CI

1. Изучи репозиторий и определи, как проверять исходный код и запускать тесты.
2. Определи события, при которых workflow должен запускаться для pull request и изменений в основной ветке.
3. Настрой GitHub Actions с понятными названиями этапов и минимально необходимыми разрешениями.
4. Добавь проверку исходного кода и запуск тестов с понятным результатом при ошибке.
5. При необходимости допиши отсутствующие тесты и проверки.
6. Настрой сборку Docker-образа без передачи секретов в образ.
7. Убедись, что workflow не публикует образ по событию pull request.
8. Создай контролируемое нарушение и получи красный запуск; зафиксируй причину ошибки.
9. Исправь нарушение и получи зелёный запуск.
10. Убедись, что секреты не раскрываются в логах.

## Задача 3. Выпусти версию в учебный кластер

### Модель выпуска

Проведи один и тот же проверенный образ через два окружения: сначала `dev`, затем `prod`. Для этого учебного стенда оба окружения могут находиться в одном кластере, но должны иметь отдельные namespace, Deployment и Service. Один и два Pod — это количество реплик, а не разделение окружений и не граница безопасности. Namespace в одном учебном кластере тоже не равен изоляции двух production-кластеров.

Сборка и публикация образа уже выполняются GitHub Actions. Не настраивай автоматический доступ GitHub runner к локальному Multipass-кластеру: в этой практике продвижение между окружениями контролируется вручную. Не пересобирай образ между dev и prod — продвигай тот же опубликованный артефакт. Для точной идентификации запиши digest образа; если используешь теги, выбери неизменяемый тег коммита, а не `latest`.

### Как разложить Kubernetes-манифесты

Храни манифесты в Git рядом с проектом, например в `k8s/`. Для двух похожих окружений есть три распространённых варианта:

- **Два полных набора YAML** (`k8s/dev/` и `k8s/prod/`) — проще всего понять в начале, но общие настройки со временем могут разойтись.
- **Kustomize base и overlays** — подходящий вариант для этой практики: `base/` хранит общие Deployment, Service и ConfigMap, а `overlays/dev/` и `overlays/prod/` задают namespace и отличия окружений. Kustomize входит в `kubectl`, отдельный Helm chart для этого задания не нужен.
- **Helm chart с values для окружений** — полезен, когда нужен шаблон с большим количеством настраиваемых параметров или его будут устанавливать в разных проектах. Для этой задачи это добавит лишний слой.

Ориентир для структуры Kustomize:

```text
k8s/
  base/
    deployment.yaml
    service.yaml
    configmap.yaml
    kustomization.yaml
  overlays/
    dev/
      namespace.yaml
      kustomization.yaml
      config-patch.yaml
    prod/
      namespace.yaml
      kustomization.yaml
      config-patch.yaml
```

Это только ориентир, не готовые манифесты: выбери, какие отличия удобнее выразить patch-файлами, а какие — настройками `kustomization.yaml`. Обычно общими оставляют селекторы Service, labels, порты, probes и базовые настройки контейнера; для окружений задают namespace, `APP_ENV`, число реплик и ссылку на образ. Перед применением изучи собранный Kustomize-результат (`build`) и проверь, что namespace и образ именно те, которые ожидаешь.

Не путай patch как файл декларативной конфигурации Kustomize с разовой командой `kubectl patch`. Первый хранится в Git и повторяем; вторая меняет объект в кластере напрямую и может оставить кластер не совпадающим с файлами. Для обычного выпуска меняй YAML/overlay в ветке и проводи изменение через PR, а не используй разовую команду как источник истины.

### Этап 1. Подготовь выкладку в dev

1. Зафиксируй исходное состояние кластера, контекст, рабочий образ и способ отката.
2. Проверь собранный Kustomize-вывод dev: namespace, ConfigMap, реплики и образ. Убедись, что тег/digest опубликован и образ подходит архитектуре worker. Base напрямую не применяй.
3. Примени только `k8s/overlays/dev` через отдельный kubeconfig и явный контекст.

### Этап 2. Проверь dev

1. Дождись завершения rollout; проверь Pod, Service и EndpointSlice.
2. Из отдельного Pod проверь `/healthz`, `/api/info` и новые маршруты по DNS Service. Во время обновления продолжай запросы и запиши ответы и готовые endpoints.
3. Подтверди фактически запущенные версию и архитектуру. Запиши результаты и ограничения проверок.

### Этап 3. Продвинь тот же образ в prod

1. После успешных проверок dev подготовь продвижение версии: в отдельной ветке измени ссылку на образ в `k8s/overlays/prod/kustomization.yaml`, указав **тот же digest**, который прошёл dev. Образ не пересобирай.
2. До PR собери prod overlay и проверь итог: namespace должен быть `content-prod`, а digest — совпадать с проверенным в dev. В PR укажи digest и краткие результаты dev-проверок; попроси ревью.
3. После одобрения и слияния примени prod overlay вручную тем же kubeconfig и явным контекстом. GitHub-hosted runner не имеет сетевого доступа к локальному Multipass-кластеру, поэтому workflow пока не может применить эти манифесты.
4. Проверь завершение rollout, готовность Pod и ответы API в prod. Зафиксируй, что запущен тот же digest, что проверялся в dev.

**Как это автоматизируют дальше:** для GitOps обычно устанавливают Argo CD или Flux в кластере и связывают контроллер с Git-каталогом манифестов. После слияния PR контроллер сам замечает обновлённый prod overlay и синхронизирует его с кластером; кластеру не нужно открывать вход для GitHub runner. В этой практике пока выполни контролируемый ручной apply после PR, а GitOps оставь отдельным следующим упражнением. Не добавляй сейчас workflow с kubeconfig в GitHub Actions: runner всё равно не может достучаться до локального кластера.

### Этап 4. Проверь prod и зафиксируй итог

1. Если все проверки prod прошли — запиши результат и завершай этап.
2. Если проверки не прошли, останови дальнейшее продвижение и собери диагностику: статус Deployment и Pods, историю rollout, события namespace и логи приложения. Не удаляй Deployment или Service.
3. Основной способ отката в этой практике — вернуть предыдущий рабочий digest в `k8s/overlays/prod/kustomization.yaml` отдельным коммитом через PR. После одобрения примени prod overlay; дождись завершения rollout и проверь Pod, Service, EndpointSlice и API.
4. Для аварийного восстановления можно выполнить `kubectl rollout undo deployment/content-deployment -n content-prod`, если доступна предыдущая ревизия Deployment. Это немедленно вернёт кластер к прошлой ревизии, но не изменит Git-манифесты. Поэтому после аварийного отката обязательно верни в Git тот же рабочий digest через PR и сверь собранный overlay с состоянием кластера.
5. Запиши причину отката, восстановленный digest, результаты проверок и выбранный способ. Зафиксируй ограничение стенда: один worker остаётся общей точкой отказа, а два namespace в одном кластере не дают production-уровня изоляции.

## Задача 4. Неудачный релиз и восстановление

1. Подготовь контролируемый вариант следующего выпуска, который не достигает готовности.
2. Примени его, не удаляя Deployment и Service.
3. Исследуй ход и результат rollout.
4. Изучи события, доступность приложения и историю релизов.
5. Выполни откат на рабочую версию.
6. Проверь работоспособность приложения после отката.
7. Убедись, что манифесты соответствуют фактическому состоянию кластера.
8. Сохрани учебные VM, историю и результаты диагностики.

## Задача 5. Защита и передача результата

1. Подготовь ссылку на pull request и ссылки на красный и зелёный запуски workflow.
2. Для красного и зелёного запусков укажи результат и понятную причину.
3. Запиши версии образов, состояние кластера и результаты проверок.
4. Объясни, почему CI и CD — разные этапы.
5. Опиши, что происходит между GitHub и container runtime на worker.
6. Объясни, почему readiness влияет на доступность Pod через Service.
7. Опиши, как откатить релиз и что делать при несовместимой миграции базы данных.
8. Укажи использованные подсказки и затраченное время.

## Границы

- Работай только с учебным проектом и кластером; используй отдельный kubeconfig `.work/kubeconfig.yaml` и явный контекст.
- Не используй реальные токены в репозитории, Dockerfile или логах.
- Не выполняй автоматический деплой с GitHub runner в локальный кластер: сетевой доступ для него пока не настроен.
- Релиз в кластер на этом этапе контролируемый и выполняется вручную.
- Не считай релиз проверенным только потому, что workflow зелёный или Pod имеет статус Running.
- Проверяющего пока нет: реальные GitHub Actions и кластер проверяются вместе.
- Если понадобится помощь, попроси подсказку, а не готовое решение.
