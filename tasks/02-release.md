# День 2. Pull request, CI и выпуск приложения

## Рабочая ситуация

Разработчик подготовил изменение API в отдельной ветке и открыл pull request. В нём меняется обычный файл приложения `app/server.py`, а не создаётся отдельная папка с новой копией. Ваша команда перед выпуском должна проверять изменения и собирать контейнер. Сейчас в репозитории нет готового CI: тебе нужно спроектировать и реализовать его самому.

Продолжай работать на своём кластере первого дня в Multipass. Ориентир — 5 часов, из них около 3–3,5 часов на Kubernetes и диагностику; если не хватит, фиксируем результат и продолжаем. Подсказки доступны по запросу, готовый pipeline не предоставляется.

## Задача 1. Прими изменение как инженер

Изучи pull request и изменения приложения. Определи, что изменилось в API, совместима ли новая версия со старой и как убедиться в работоспособности. Зафиксируй исходное состояние кластера, Deployment, образа, Service, EndpointSlice и ответы текущего API. Не меняй кластер, пока не знаешь, как восстановить исходную версию.

## Задача 2. Построй CI

Самостоятельно настрой GitHub Actions для pull request и изменений в основной ветке. Требования:

- проверка исходного кода и запуск тестов из репозитория с понятным результатом при ошибке;
- сборка Docker-образа без передачи секретов в образ и без публикации по событию pull request;
- понятные названия этапов, минимальные необходимые разрешения workflow, воспроизводимость;
- продемонстрируй сначала красный запуск на контролируемом нарушении и затем зелёный запуск на исправленном коде. Не раскрывай секреты в логах.

При необходимости допиши отсутствующие тесты и проверки. Не подключай боевые учётные данные и не публикуй образ из PR.

## Задача 3. Выпусти версию в учебный кластер

Собери и доставь образ новой версии в container runtime Multipass worker с совместимой архитектурой. Выбери способ доставки и версионирования и объясни его. Через свои Kubernetes-манифесты выполни rolling update двух реплик. Сохрани доступность Service и конфигурацию, задай осмысленные readiness/liveness и ограничения ресурсов.

Из отдельного Pod проверь API через DNS и Service до, во время и после обновления. Собери данные о результатах запросов и о готовых endpoints. Подтверди новую версию и работоспособность новых маршрутов. Объясни, что именно твои проверки доказывают и чего не доказывают; один worker остаётся общей точкой отказа.

## Задача 4. Неудачный релиз и восстановление

Создай контролируемый вариант следующего выпуска, который не достигает готовности. Не удаляй Deployment и Service. Исследуй rollout, события, доступность и историю, затем выполни откат на рабочую версию. Убедись, что манифесты снова соответствуют фактическому состоянию. Не удаляй учебные VM, историю и результаты.

## Задача 5. Защита и передача результата

Покажи ссылку на pull request и зелёный и красный запуски с понятными причинами, версии образов, состояние кластера и результаты проверок. Кратко объясни: почему CI и CD — разные этапы; что происходит между GitHub и container runtime на worker; почему readiness влияет на Service; как откатить релиз и что делать с несовместимой миграцией базы. Укажи использованные подсказки и время.

## Границы

- Работай только с учебным проектом и кластером; используй отдельный kubeconfig `.work/kubeconfig.yaml` и явный контекст.
- Не используй реальные токены в репозитории, Dockerfile или логах. Не выполняй автоматический деплой с GitHub runner в локальный кластер: сетевой доступ для него пока не настроен. Релиз в кластер на этом этапе контролируемый и выполняется вручную.
- Релиз нельзя считать проверенным только потому, что workflow зелёный или Pod имеет статус Running.
- Проверяющего пока нет: мы проверим реальные GitHub Actions и кластер вместе. Если понадобится помощь, попроси подсказку, не готовое решение.
